# GSC content optimization loop

Цей цикл не публікує AI-редагування напряму. Раз на приблизно 14 днів він бере фіналізовані дані Google Search Console, знаходить сторінки з достатньою кількістю показів і слабкою віддачею, порівнює їх із сильнішими сторінками сайту, редагує максимум 3 статті та відкриває окремий PR для ручного merge.

## Логіка відбору

- 28 днів поточних GSC даних проти попередніх 28 днів;
- затримка 3 дні, щоб не спиратися на надто свіжі дані;
- мінімум 60 impressions;
- середня позиція не гірша за 30;
- сторінці щонайменше 21 день від останнього `lastmod` у sitemap;
- одну сторінку не переписувати частіше ніж раз на 42 дні;
- максимум 3 переробки за цикл;
- сильні сторінки визначаються з тих самих GSC даних, а їх production HTML використовується як структурний референс.

Система не копіює текст сильних статей і не змінює slug. Вона переносить принципи, які можна побачити у сторінок з кращими результатами: відповідність intent, title/meta/H1, конкретність вступу, структура H2, життєві приклади, механізм і практичні дії.

## Необхідні GitHub Secrets

`GSC_SITE_URL` — точна назва property у Search Console, наприклад URL-prefix або `sc-domain:...`.

`GSC_SERVICE_ACCOUNT_JSON` — повний JSON service account. Цей service account треба додати користувачем у відповідну Search Console property з правом читання.

`OPENAI_API_KEY` — ключ для автоматичного редактора.

Необов’язково: `OPENAI_MODEL`. Якщо не заданий, використовується модель із `config.json`.

## Безпека SEO

Автоматизація не merge-ить PR і не змінює production сама. Після кожного merge потрібен звичайний SEO/production контроль. Історія переробок зберігається в `history.json`, щоб одна стаття не переписувалась кожні два тижні без часу на накопичення нових даних.
